# 일반 보기와 원본 과부하 실험

## 변경 내용

이전에는 원본 도착률(재생 구간 약 3.69건/초)을 단일 작업 처리 서버 3대에 그대로 적용해 큐가 지속적으로 증가했습니다. 처리 가능한 요청만 세어도 약 3.42건/초이며, 처리 속도 가정의 처리 능력은 약 0.57건/초였습니다. 표시 오류가 아닌 과부하였습니다.

기본 화면은 `standard` 모드입니다. 원본의 도착 간격만 9배로 늘립니다. 첫 시각, 순서, 동시 도착, 요청 수, 입력/실제 출력 길이, 블록 ID는 유지합니다. 서버의 처리 속도나 출력 길이를 줄이거나 큐 표시를 잘라내지 않습니다. 지연은 변경된 도착 시각부터 계산합니다.

`original` 모드는 원본 시각을 그대로 사용합니다. 상단의 접힌 ‘실험 모드’에서 선택할 수 있습니다. 모드 전환은 해당 방문자의 재생만 초기화하고 시작합니다. 새로 접속하면 일반 보기를 기본으로 시작합니다.

## 간격 산정

`backend/replay.py`는 과거 학습 8,421건만 사용합니다. 입력+출력 예약이 32,768토큰 안에 드는 요청의 도착률과 역사적 평균 처리 시간을 구합니다.

간격 배수 = ceil(과거 도착률 × 과거 평균 처리 시간 ÷ (서버 3대 × 목표 부하 0.65))

현재 값은 9입니다. 실제 GPU 실측이나 학습된 라우팅 가중치가 아닌 **시연 부하 설정**입니다. 평가 구간의 미래 출력 길이는 간격 산정에 사용하지 않습니다. 학습이 비활성화된 환경은 고정 대체 설정 9를 사용합니다. 배속은 시간 전체를 앞당기는 별개 설정이며 공개 화면에서는 1배속입니다.

## 전체 재생 검증 (2026-10-23)

`python -m tools.audit_traffic_modes`로 학습된 출력 예측 모델을 사용해 최종 재생 1,805건을 끝까지 검사했습니다. 각 도착 시각에서 실제 큐를 집계한 결과입니다.

|모드|유입 간격|서버 A/B/C 최대 큐|도착 종료 시 큐|완료/거절|
|---|---|---|---|---|
|일반|9배|8 / 8 / 9|1 / 2 / 1|1,671 / 134|
|원본|1배|459 / 454 / 475|459 / 454 / 475|1,671 / 134|

두 모드 모두 최종 큐가 0이 될 때까지 처리 완료했습니다. 거절은 기존 입력+출력 예약 한도에 따른 것으로 원본 요청을 삭제하지 않습니다. 일반 보기의 큐가 9 이하였다는 것은 이 데이터와 설정의 실험 결과이지 강제 상한이나 모든 입력에 대한 보장은 아닙니다. 유입량 자체가 다르므로 이 차이를 로드밸런싱 알고리즘 개선 효과로 주장하면 안 됩니다. 정책 비교는 같은 모드·초기 상태에서 수행해야 합니다.

단위 테스트 31개 통과. 원본 불변, 동시 도착 유지, 모드별 시각 메타데이터, 방문자별 모드 독립, 원본 과부하 및 일반 안정화, 전체 요청 처리 완료를 검사했습니다.

공개 HTTPS에서도 두 독립 세션을 600초씩 진행했습니다. 일반: 도착 271건, 큐 2/3/4. 원본: 도착 1,805건, 큐 433/434/454. 두 세션의 모드 변경이 서로 영향을 주지 않았습니다.
