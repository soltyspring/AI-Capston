# 출력 토큰 예측 모델 개선 및 학습 기록

2026-11-15 첫 학습 기준. 이 문서는 **실제 GPU 상시 실험에서 쌓인 응답 기록**으로 출력 토큰 예측기를 개선한 과정을 설명한다. Mooncake 시뮬레이터의 랜덤 포레스트는 [별도 문서](output-prediction.md)에 있다. 답변을 생성하는 LLM이나 서버를 고르는 LinUCB를 다시 학습한 작업은 아니다.

## 1. 오차가 큰 이유

첫 자연 종료 100건의 실제 출력 합은 **6,358토큰**, 절대 오차의 합은 **81,794토큰**이었다. 요청당 실제 출력은 평균 63.6토큰인데, 평균 절대 오차는 817.9토큰이었다. 대시보드의 오차율은 `절대 오차 합 ÷ 실제 출력 합 × 100`(WAPE)이므로 **1,286.5%**까지 올라갔다. 실제 출력보다 절대 오차 합이 크면 이 지표는 100%를 넘을 수 있다.

별도 GPU 비교에서 입력 36토큰인 요청을 **449토큰**으로 예측했지만 실제로는 **24토큰**에서 끝났다. 기존 운영 예측기는 입력 토큰 수와 질문 분류를 넘겨받는다. 분류가 같아도 “한 문장으로 답해 줘”와 “단계별로 자세히 설명해 줘”는 답변 길이가 다르므로, 원문에 있는 길이 지시를 추가로 반영했다.

## 2. 학습 데이터와 정답

| 데이터 | 출처 | 활용 |
| --- | --- | --- |
| 질문 원문 | `workload/requests.jsonl` | 요청 인덱스로 실험 결과와 연결하고 길이 지시를 추출 |
| 입력 토큰, 실제 출력 토큰, 출력 상한, 기록 시각 | `central-training.sqlite3`의 `samples` | 입력 특징, 학습 정답 또는 하한, 시간순 분할 |
| 기존 모델의 예측, 종료 이유 | 같은 DB의 `length_evaluation` | 새 기록에서는 배정 당시 예측과 종료 이유 사용 |

완료된 요청 중 입력이 1~15,872토큰이고 실제 출력이 1토큰 이상, 설정한 출력 상한 이하인 건만 사용했다. 앞 **8,778건**으로 학습하고, 이후 **2,195건**은 검증에만 사용했다. 표준화에 쓰는 평균과 표준편차도 학습 구간에서 계산한다. 요청을 예측할 때는 실제 출력 길이와 종료 이유를 입력으로 사용하지 않는다.

출력 한도 때문에 잘린 응답과 자연스럽게 끝난 응답은 다르게 처리한다.

- `stop`: 24토큰에서 끝났다면 **24토큰을 정답**으로 사용한다.
- `length`: 128토큰 상한에서 잘렸다면 **128토큰 이상**이라는 정보만 사용한다. 한도가 없었을 때의 길이는 알 수 없다.
- 이전 기록: 종료 이유가 없어 **상한 미만이면 자연 종료로 간주**했다. 저장된 기존 예측값이 없는 건은 기존 분류기와 예측기로 다시 계산했다.

## 3. 개선 모델 학습 방식

기존 예측값을 하나의 입력으로 활용하는 **로그정규 회귀**를 추가했다. 입력은 다음 여섯 가지다.

| 입력 특징 | 역할 |
| --- | --- |
| `log(1 + 입력 토큰 수)` | 모델이 읽을 글의 양 |
| `log(1 + 기존 예측 토큰 수)` | 기존 모델이 추정한 답변 길이 |
| 짧은 답변 지시 여부 | `한 문장`, `짧게`, `one sentence` 등 |
| 긴 답변 지시 여부 | `자세히`, `단계별`, `step by step` 등 |
| `log(1 + 명시한 길이 제한)` | `50토큰 이내`, `at most 20 words` 등. 단어 수는 특징을 만들 때 2배로 환산하는 단순 근사를 사용 |
| `log(1 + 질문 글자 수)` | 토큰 수와 함께 입력 길이 보완 |

출력 토큰 수를 로그로 바꾼 뒤, 자연 종료 건은 관측된 길이를 설명하고 한도에서 자른 건은 관측값 이상일 확률을 높이도록 학습한다. 이를 **우측 검열** 처리라고 한다. SciPy의 `L-BFGS-B`로 계수를 최적화하고, 계수가 지나치게 커지지 않도록 L2 규제를 적용했다. 예측할 때는 로그값을 토큰 수로 되돌려 반올림하고 1~4,096토큰 범위로 제한한다.

완료된 응답에서 실제 길이를 얻고 이를 정답 또는 하한으로 사용하는 **지도학습**이다. 새 요청의 결과는 계속 수집하지만, 수집될 때마다 모델이 자동으로 다시 학습되지는 않는다.

## 4. 첫 검증 결과

| 지표 | 평가 대상 | 기존 예측기 | 개선 예측기 |
| --- | --- | ---: | ---: |
| 제한 적용 전 평균 절대 오차(MAE) | 출력 상한 미만 398건 | 839.4토큰 | **460.4토큰** |
| 제한 적용 전 절대 오차율(WAPE) | 같은 398건 | 1,247.6% | **684.3%** |
| 요청별 출력 상한 적용 후 평균 절대 오차(MAE) | 전체 2,195건 | 23.4토큰 | **17.3토큰** |

출력 상한 미만 요청의 평균 절대 오차는 약 **45% 감소**했지만, 해당 요청의 실제 평균 출력이 67.3토큰이라는 점을 고려하면 오차가 여전히 크다. 마지막 행은 두 모델의 예측을 각각 요청 상한으로 자른 뒤 비교한 값이다. 상한이 없는 답변 길이까지 잘 예측한다는 의미는 아니다. 첫 검증에서는 종료 이유가 확인된 응답이 없어 398건을 상한 미만 기준으로 골랐다.

코드는 상한 미만 그룹 MAE가 기존보다 **10% 넘게 감소**하고, 전체의 상한 적용 MAE가 증가하지 않으며, 상한 적용 후 평균 과소예측량이 기존보다 5토큰 넘게 증가하지 않아야 후보를 승인한다. 승인은 상시 실험에서 비교할 수 있다는 뜻이다. 실제 운영 라우팅은 기존 값을 사용하며, 지연 개선 효과는 별도의 동일 부하 비교가 필요하다.

## 5. 실행과 배포 후 검증

aic-10에서 `joblib`, `numpy`, `scipy`와 기존 모델을 읽을 수 있는 환경으로 실행한다. 저장된 실험 요청 파일과 SQLite가 필요하며, 학습은 DB를 읽기 전용으로 연다.

```bash
python deploy/aic-10/train_length_forecast.py \
  --workspace "$HOME/.local/share/qless-training" \
  --router "$HOME/round"
```

학습 결과는 작업 디렉터리의 `output-length-candidate.json`에 저장된다. 이 파일에는 전처리 값, 회귀 계수, 검증 결과와 학습 시각이 들어 있다. 상시 실험 수집기는 승인된 후보를 읽고, 서버 배정 정보가 도착했을 때 후보의 예측을 계산한다. 답변이 끝나면 같은 요청에 대해 **기존 예측·개선 예측·실제 출력·종료 이유·후보 버전**을 저장한다. [상세 분석](https://qless.bluecl.cloud/#analysis)은 최신 후보 버전에서 실제 자연 종료(`stop`)가 확인된 동일 응답으로 두 예측기의 오차율을 비교한다.

## 6. 주제·키워드·답변 형식의 효과 비교

새 후보에서는 금융·개발·의료 등 주제 단서, 학습 요청에서만 고른 최대 96개 단어의 등장 여부, 표·목록·코드·JSON·문단 등의 형식과 항목 개수를 추가했다. 기존 예측기와 이전 개선 후보는 바꾸지 않았다. 학습 9,685건 이후의 동일 검증 2,422건을 모든 후보에 사용했고, 아래 첫 수치는 종료 이유가 실제로 `stop`인 161건에서 계산했다.

| 모델 | 자연 종료 MAE | 출력 상한 적용 전체 MAE |
| --- | ---: | ---: |
| 기존 운영 모델 | 847.86 | 23.87 |
| 이전 개선 모델 | 544.94 | 17.24 |
| 기본 특징만 같은 데이터에서 다시 학습 | 542.07 | 17.19 |
| 주제·키워드·형식 모두 사용 | 505.31 | 17.05 |

다른 특징의 구성은 유지한 채 하나씩 제거해 다시 학습했다. 전체 특징 모델과 비교하면 형식을 넣었을 때 자연 종료 MAE가 **53.25토큰 감소**, 키워드를 넣었을 때 **6.68토큰 감소**, 주제를 넣었을 때 **8.45토큰 증가**했다. 이는 이번 데이터에서의 조건부 효과이며, 세 값을 합산할 수 없다. 전체 상한 적용 오차에서는 키워드를 뺀 모델이 더 나았다. 다음 검증에서는 주제를 뺀 구성을 새로운 요청 묶음과 미사용 질문 템플릿에 비교할 필요가 있다.

같은 학습 명령은 현재 `output-length-candidate-v2.json`(후보)과 `output-length-comparison.json`(집계 비교)을 별도로 생성한다. 현재 운영 모델과 상시 실험의 이전 후보는 그대로이며, [상세 분석](https://qless.bluecl.cloud/#analysis)에 오프라인 비교 결과를 공개한다.

## 7. 1,000건 단위 지도학습과 배정 정책 평가

- 기존 상시 실험의 저장 위치에서 시작한다. 새 학습 구간 1,000개 요청을 처리한 뒤, 형식·키워드 기반 지도학습 예측기와 실험 LinUCB 계수를 체크포인트로 저장한다. 과거 및 최신 기록 중 평가 구간보다 앞선 최대 8,000건을 예측 학습에 사용한다. 별도 주제 특징은 제외하며 키워드가 특정 주제를 간접적으로 드러낼 수는 있다.
- 다음 1,000개 요청은 저장한 모델을 고정해 평가한다. 실험 LinUCB는 읽기 전용 계수로 점수를 매기며 평가 중 계수를 갱신하지 않는다. 해당 구간의 출력 기록은 평가가 끝난 이후의 예측기 학습에는 사용될 수 있다.
- 각 요청 묶음을 같은 출력 예측기, 질문, 동시 요청 수, 출력 상한으로 Round Robin, 예상 완료 시간 최소, 실험 LinUCB에 보내고 실행 순서는 묶음마다 바꾼다. GPU 3대가 모두 정상일 때 평가하므로 1,000개 질문당 GPU 호출은 최대 3,000건이다. 사용자의 요청이 먼저이며 중단된 실험은 저장된 위치부터 이어간다. 공개 지표는 요청 원문을 포함하지 않는다.
- 예측 오차는 실험 LinUCB 실행에서 `stop`으로 끝난 실제 응답 하나를 기준으로 기존·개선 예측기의 MAE를 비교한다. 정책은 첫 응답과 완료 P95, 실패 수를 따로 표시한다. 모델 출력과 캐시가 실행마다 달라질 수 있으므로 실측 간격이 작은 차이는 여러 구간에서 재확인한다.
- 실험에는 출력 상한을 유지한다. `length` 종료는 정답이 아니라 하한으로 처리한다. 자연 종료 표본을 더 확보하려면 동일한 모델 설정으로 별도 고상한 요청 묶음을 설계해 수집한다.
