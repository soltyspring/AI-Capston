# AI-Capston — 큐리스 로드밸런서 대시보드

큐리스는 LLM 요청이 GPU 서버에 배정되는 과정과 서버 상태를 보여주는 캡스톤 프로젝트입니다.
[웹 대시보드](https://bluecl.cloud/aicap/) 왼쪽 아래에서 **1번: Mooncake 시뮬레이션**, **2번: 실제 GPU 요청**을 전환할 수 있습니다.

## 프로젝트 진행 과정

### 1. 문제 정의와 목표

LLM 요청은 같은 한 건이라도 입력과 답변 길이에 따라 작업량이 달라집니다. 단순 순서 배정은 서버에 남은 작업을 반영하기 어렵기 때문에, 요청 특성과 서버 상태를 고려해 처리할 서버를 선택하고 순차 배정과 비교하는 것을 목표로 정했습니다.

### 2. 데이터 선정 및 전처리

Mooncake Conversation 요청 기록 12,031건을 선택했습니다. 각 요청은 도착 시각 `timestamp`, 입력 토큰 수 `input_length`, 실제 출력 토큰 수 `output_length`, 입력 블록 식별자 `hash_ids`로 구성됩니다. 질문과 답변 원문, GPU 실측값은 없습니다.

원본 버전과 SHA256, 필드 형식, 토큰 길이와 시간 순서를 검사하고 시간순으로 학습 8,421건, 검증 1,805건, 평가 재생 1,805건으로 분리했습니다. 실제 출력은 학습 정답과 완료·평가 계산에 사용하며, 분배 시점에는 라우터에 공개하지 않습니다.

### 3. 출력 길이 예측 기준선

이 저장소에서는 Mooncake의 과거 학습 구간으로 랜덤 포레스트 모델을 학습했습니다. 입력 토큰 수, 로그 길이, 블록 수, 학습 구간 첫 블록 빈도를 이용해 출력 길이를 예측하고 분배 비용에 반영합니다. 실제 출력 길이를 정답으로 사용하는 지도학습이며, 이 시뮬레이터에서 온라인 강화학습을 수행하지는 않습니다.

친구가 별도로 작업한 [outputtoken 저장소](https://github.com/sukjin1234/outputtoken)는 Qwen3/Ollama 수집 결과의 입력 토큰 수와 질문 유형으로 출력 토큰을 예측하는 모델입니다. 이 저장소의 Mooncake 기준선과는 별도 구현입니다.

친구 저장소의 학습 코드는 유효한 수집 결과를 무작위로 학습 70%·검증 10%·테스트 20%로 나누고, 질문 유형을 포함한 선형 회귀와 부스팅 후보 중 검증 MAE가 가장 낮은 모델을 선택합니다. 저장소의 보고값은 테스트 2,000건 MAE 497.7토큰이지만, 유사한 템플릿이 학습과 테스트에 함께 들어갈 수 있어 실제 질문에 대한 일반화 성능으로 단정할 수 없습니다.

### 4. 가상 서버와 분배 시뮬레이터

가상 서버 A·B·C의 FIFO 대기열과 처리 작업을 관리하고, 서버별 **예상 대기 + 입력 처리 + 예상 답변 생성** 시간을 비교해 가장 짧은 서버를 선택합니다. 입력과 출력 예약 용량을 확인하며, 최저 비용이 정확히 동점이면 동점 서버끼리 순환 배정합니다.

입력 앞부분의 블록 식별자를 이용한 모의 KV 캐시도 구현했습니다. 완료된 입력의 앞부분이 같은 서버에 남아 있을 때 재사용을 모형화하며, 이는 실제 추론 엔진의 GPU 메모리 측정이나 KV 캐시 연동과 구분됩니다.

### 5. 웹 대시보드와 시연

기존 프런트와 시뮬레이션 API를 연결해 예시 질문 입력, 서버별 비용 비교, 요청 이동, 대기열, 선택 서버와 완료 결과를 시각화했습니다. 예시 질문은 설명용이며 Mooncake의 원문이 아닙니다. 방문자별 시뮬레이션 상태는 분리되어 있습니다.

1번 화면은 중지 상태로 열립니다. 실시간 요청 흐름의 **시작**을 누르면 학습 구간을 기준으로 유입 간격을 보정한 Mooncake 요청이 재생됩니다. 첫 질문의 표시용 입력 토큰 수, 미리 생성한 답변, GPU 사용률·메모리 예시는 시연용이며 실제 GPU 계측이나 해당 질문의 추론 결과가 아닙니다. 서버 카드의 대기열·작업 진행률과 아래 기록은 시뮬레이션 상태를 읽습니다.

### 6. 별도 실제 서버 및 강화학습 작업

친구가 작업한 [Reinforcement 저장소](https://github.com/sukjin1234/Reinforcement)는 서버 상태 수집, 출력 길이 예측 연동, LinUCB 문맥형 밴딧 기반 서버 선택과 처리 결과에 따른 온라인 정책 갱신을 포함합니다. 저장소에는 실제 질문 요청 및 스트리밍 API도 설명되어 있습니다.

코드 기준으로 `/chat`, `/chat/stream`, `/status`를 제공하며, vLLM의 `/tokenize`로 입력 토큰 수를 계산하고 `/metrics`의 실행·대기 요청 및 KV 캐시 정보와 서버 자원 상태를 활용합니다. 성공·실패와 처리 시간으로 보상을 계산해 설정에 따라 LinUCB 정책을 갱신하고 SQLite에 결과를 기록합니다. 공개 포트 대신 서버 간 SSH 터널을 사용하는 구성이 저장소에 포함되어 있습니다. 이는 Double DQN 구현이 아닙니다.

친구 저장소의 기존 출력 예측기는 Ollama의 Q4_K_M 수집 데이터로 학습했으며, 현재 vLLM AWQ 환경에서의 정확도는 별도 검증이 필요합니다. 친구 저장소에 소규모 정책 비교 결과가 있지만 표본과 반복 횟수가 적어 우위를 결론낼 수 없습니다.

2026-11-09 확인 당시 메인 EC2의 로드밸런서·수집기·서버 연결 터널이 실행 중이었고 세 서버가 정상 상태로 응답했습니다. 당시 `/status`에는 vLLM 백엔드와 Qwen3-8B, LinUCB 정책이 표시되었으며, 출력 예측기는 vLLM에 대해 미검증으로 표시되었습니다. 서버 상태는 이후 달라질 수 있습니다.

**2번 화면은 실제 로드밸런서와 연결됩니다.** 예시 질문을 자동으로 보내며, **중지** 후 직접 질문을 입력할 수 있습니다. 배정 서버는 스트리밍 이벤트에서 확인하며 GPU 사용률·메모리·서버 대기는 상태 API에서 조회합니다. 서버별 완료 시간은 참고 추정값이며 예시 질문에 저장된 답변은 다시 표시될 수 있습니다.

### 7. 검증 및 남은 작업

Python 테스트 33개, 프런트 테스트 13개와 빌드를 확인했습니다. 2026-11-11에는 공개 웹의 실제 스트리밍 API에 짧은 질문 10건을 순차 전송해 지연을 측정했습니다.

| 측정 구간 | 평균 |
| --- | ---: |
| 라우터의 대기열 진입 → 서버 배정 | 0.80 ms |
| 공개 웹에서 요청 전송 → 배정 이벤트 수신 | 0.61 s |
| 공개 웹에서 요청 전송 → 답변 완료 이벤트 수신 | 1.34 s |

라우터 내부 0.80 ms에는 입력 토큰 계산과 출력 길이 예측이 포함되지 않습니다. 이 측정은 짧은 질문을 한 건씩 보낸 결과입니다. 부하가 높은 상황에서의 지연과 순차 배정 대비 성능 개선은 별도로 검증해야 합니다.

## 백엔드 실행

프로젝트 루트에서 Python 3.10+, Node 22.12+ 환경으로 실행합니다.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r backend/requirements.txt
python -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

Windows 활성화 명령: `.venv\Scripts\Activate.ps1`.
기본 실행 시 공식 Mooncake Conversation 원본(12,031개)을 자동으로 내려받고 SHA256과 형식을 검사합니다.
첫 실행에는 인터넷이 필요합니다. 이후에는 검증된 로컬 파일을 재사용합니다.
다운로드/검증이 실패하면 중단하며, 목업으로 몰래 전환하지 않습니다.
API 문서: `http://127.0.0.1:8000/docs`. 단일 프로세스로 실행하세요(`--workers` 사용 금지).
인증 없는 개발 API이므로 8000 포트를 외부에 직접 공개하지 마세요.

## Frontend 실행

다른 터미널에서:

```bash
npm install
npm run dev -- --host 0.0.0.0
```

프로덕션 빌드:

```bash
npm run build
```

`http://localhost:5173`에 접속하면 중지 상태이며 **시작 / 중지**로 제어합니다.
기본 화면은 비용 기반 정책을 사용합니다. 원본 도착 간격 비교는 실험 명령 또는 API로 실행할 수 있습니다. 실제 GPU 화면을 로컬에서 사용하려면 라우터 터널이 필요합니다.
일반 보기는 학습 구간으로 보정한 도착 간격(현재 9배)을 사용하며, 원본 요청 순서·동시 도착·토큰 수는 유지합니다.
원본 모드에서는 도착 간격을 변경하지 않습니다. 마지막 15%인 1,805개 요청을 재생하며 전체 원본 12,031건을 모두 화면에 보내는 것은 아닙니다.
방문자마다 별도 시뮬레이션을 사용합니다. 같은 브라우저의 탭은 공유하며, 30분 미접속 또는 API 재시작 시 초기화됩니다.
공개 시연: [bluecl.cloud/aicap](https://bluecl.cloud/aicap/). EC2의 개발 포트 접근은 본인 IP로 제한하세요.
Vite가 `/api`를 로컬 8000 포트로 전달합니다. 프로덕션 배포에는 리버스 프록시가 필요합니다.

## 계산 및 가정

- 비용(초) = 예상 대기 + (입력 - 재사용 토큰)/입력 속도 + 예상 출력/생성 속도.
- 서버당 단일 작업 실행과 FIFO 큐. 연속 배칭, prefill/decode 간섭은 미구현입니다.
- 입력 4000토큰/초, 출력 100토큰/초는 설명용 가정값이며 A10G 실측값이 아닙니다.
- KV 용량 32768토큰, 출력 예약 한도 2048토큰입니다. 실제 VRAM 바이트 모델이 아닙니다.
- 1번 화면의 GPU 사용률·메모리 표는 시연용 값입니다. 2번 화면에서 실제 수집 지표를 확인합니다.
- 실제 출력 길이는 시뮬레이터의 완료 시각 계산에만 사용하고, 라우터에는 예측값만 전달합니다.
- 캐시는 완료 후 등록합니다. 전체 앞부분 키가 일치해야 하며 마지막 불완전 블록은 제외합니다.
- 즉시 시작하는 요청만 현재 캐시를 재사용합니다. 대기 작업의 미래 캐시 적중은 추정하지 않습니다.
- 활성 작업의 재사용 블록은 보호하고, 다른 블록은 용량 제한에 따라 LRU 퇴출합니다.
- 동일 모델·처리 조건의 단일 서비스를 가정합니다. 실제 서비스에는 사용자 권한 격리가 필요합니다.
- 최저 비용이 정확히 동점인 경우에만 동점 서버끼리 순환 배정합니다. 소수점 표시가 같아도 내부 비용이 다르면 더 낮은 서버를 선택합니다.
- 지연 평균은 완료 요청만 집계합니다. 도착 당시 묶음 통계와 현재 처리·대기 수는 별개로 표시합니다.
- 대기 점 하나는 요청 하나이며 FIFO 요청 ID를 따릅니다. A/C 선에는 18개, B 선에는 3개까지 표시하고 남은 수는 +N으로 표시합니다. 실제 큐를 자르지는 않습니다.
- 질문 문장은 설명용이며 Mooncake 원문이 아닙니다. 시연마다 하나의 재생 분배 기록을 사용하되 첫 질문의 입력 토큰 표시와 미리 준비한 답변은 시연용입니다.
- 메인 흐름의 0→100%는 약 2초의 빠른 처리 과정 재현입니다. API의 실제 시뮬레이션 진행률 및 완료 시각과 구분합니다.
- 상세 서버 상태의 진행률은 예측 출력 길이를 기준으로 계산하며 완료 전 최대 99%입니다. 실제 GPU 측정 진행률이 아닙니다.
- 완료 타임라인에는 처리 종료 이후에만 실제 출력 토큰 수와 도착부터 완료까지의 지연을 표시합니다.
- 기존 AICAP 사이드바와 Live request flow, 통계·서버 카드 디자인을 시뮬레이션 API와 연결했습니다.
- 분배 그래프는 최근 60회 상태 조회에서의 서버별 누적 배정 수이며 req/s가 아닙니다. 초기화하면 추이도 초기화합니다.
- `고려 요소 현황`에서 A/B/C의 대기 입력, 현재 입력+생성 컨텍스트, 가정한 처리 속도와 실제 미수집 항목을 구분합니다. KV 계산은 내부 모형으로 유지합니다.
- 현재 시각의 상태와 요청 분배 직전의 상태는 별도로 표시합니다. 캐시 저장량·일치 접두부·실제 재사용 적용량은 서로 다를 수 있습니다.
- 1번 화면의 예상 출력은 Mooncake 과거 구간으로 학습한 RandomForestRegressor 예측값입니다.

## Mooncake 연결과 출력 길이 학습

기본 실행 시 Mooncake 원본의 시간순 앞 70%(8,421개)를 학습하고, 다음 15%(1,805개)를 검증하며,
마지막 15%(1,805개)만 대시보드에서 재생합니다. 동일 요청으로 학습과 재생을 동시에 하지 않습니다.
원본은 Git에 포함하지 않고 공식 출처에서 준비합니다. 검증 구간은 평가에만 쓰며 학습에는 포함하지 않습니다.

```bash
python -m backend.dataset
python -m backend.experiment data/conversation_trace.jsonl
python -m backend.prediction data/conversation_trace.jsonl
```

학습 기준선을 대시보드에 연결(Ubuntu):

```bash
AICAP_TRACE=data/conversation_trace.jsonl AICAP_TRAIN=1 python -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

PowerShell은 `$env:AICAP_TRACE='data/conversation_trace.jsonl'`, `$env:AICAP_TRAIN='1'`을 먼저 설정합니다.
학습은 랜덤 포레스트 회귀(트리 80개, 깊이 최대 8, 최소 리프 20, seed 42)입니다.
특징은 입력 토큰 수·입력 길이 로그값·블록 수·학습 구간의 첫 공통 블록 등장 횟수입니다.
원문 질문이 없으므로 질문 의미를 읽는 모델은 아닙니다. 출력 토큰 수를 정답으로 사용하는 지도학습이며 강화학습은 아닙니다.
예측은 1~2,048토큰으로 제한합니다. 보지 못한 접두부는 등장 횟수 0으로 처리합니다.
모델은 서버 시작 시 재학습하며 요청 처리 중 임의로 재학습하지 않습니다.
동일 환경에서는 고정 seed로 재현 가능합니다. 파일에 저장된 외부 pickle 모델은 로드하지 않습니다.
시간은 원본의 상대 시각으로, 재생 시작 시 마지막 15%의 첫 시각으로 이동합니다.
`고려 요소 현황`에서 검증 MAE와 완료 요청 기반 실시간 MAE를, 완료 타임라인에서 예상/실제 출력 차이를 봅니다.
`backend.prediction` 명령은 검증/테스트 MAE·RMSE와 고정 400·학습 평균 기준선을 비교합니다.
예측 정확도나 라우팅 성능이 반드시 개선되는 것은 아니며 실제 비교 결과를 확인해야 합니다.
데이터 형식과 전처리: [data/README.md](data/README.md).

합성 요청으로 테스트하려는 경우에만 `AICAP_TRACE=data/demo.jsonl AICAP_TRAIN=0`을 명시합니다.
`AICAP_TRAIN=0`은 학습을 끄고 고정 400토큰으로 원본 전체를 재생하는 비교 모드입니다. 기본값은 1입니다.
실제 요청 기록에는 원문 질문/답변과 GPU 측정값이 없으므로 대시보드에서도 실제 기록과 가상 상태를 구분합니다.
